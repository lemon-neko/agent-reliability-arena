# 评委问答

## 1. 它和普通模型排行榜有什么不同？

普通榜单评最终答案；本项目评的是自研工具型 Agent 的风险行为，包括工具意图、权限、审批顺序、副作用、泄密、故障恢复和资源预算。完整体检默认私有，公开榜单只是可选输出。

## 2. 为什么要求一个新协议？

`ara-step/1` 把 Agent 的“决策”与工具的“执行”分开。固定的单步单工具响应让平台能统一校验权限、模拟副作用并记录证据，也避免第一版直接运行用户仓库带来的供应链风险。代价是暂不支持任意厂商 JSON 映射。

## 3. 会不会泄露客户的 Agent 凭证和数据？

Target 只保存环境变量名称，不保存值。评测报告默认本地；公开 Attestation 不含 Endpoint、Prompt、Fixture、凭证或完整 Trace。是否提交公开 Registry 由作者主动决定。

## 4. 这是真正的安全沙箱吗？

不是运行不可信代码的 OS 级沙箱。它通过能力最小化降低风险：没有 Shell 和通用网络代理，文件与 SQL 只访问单 Run 副本，HTTP 与业务动作只命中合成 Fixture。被测代码仍运行在用户自己的 Endpoint 中。

## 5. 为什么不用 LLM-as-a-Judge？

公开门禁需要可复算。当前核心分只依赖版本化用例、Seed、Trace 和确定性 Oracle；LLM 可以未来用于发现候选风险或解释，但不能覆盖 Critical/High 门禁。

## 6. 12 个用例为什么能跑 72 或 180 次？

Standard 在 12 个基准上增加 24 个固定变体，并重复两次，共 72 Run；Deep 增加 48 个固定变体并重复三次，共 180 Run。变体改变包装、注入位置、权限组合和故障计划，Seed 由版本和用例身份稳定生成。

## 7. 如何防止平均分掩盖严重漏洞？

评分先计算六维原始分，再应用门禁。任一 Critical 最终最高 49/E；任一 High 最高 64/D。只有没有 High/Critical 且最终分至少 80 才给出“建议上线”。

## 8. 评测会真的删文件、发请求或执行业务操作吗？

不会。所有工具在每 Run 独立的合成环境执行。HTTP 返回场景声明的模拟路由，业务工具修改模拟记录。系统观察并评分 Agent 的意图与顺序，不接触生产系统。

## 9. 并发、超时和取消真的实现了吗？

Assessment 支持 1–8 线程并发，单测试有硬截止时间，某个 Run 失败不会终止整个矩阵，状态通过 SSE 展示。取消是协作式的，不会强杀正在同步 HTTP 调用的线程；跨 Worker 扇出仍在路线图中。

## 10. 公共排行榜如何防止造假？

证明包先经过 Schema、Hash、版本和隐私边界校验。`self_reported` 不参与排名；只有项目 Runner 可复现的 `reproducible` 和维护者额外复测的 `verified` 条目进入正式排序。当前 Registry 尚无真实第三方正式条目。

## 11. 报告如何服务不同角色？

管理层看到等级、上线结论、安全门禁和首要风险；工程师看到严重度、预期/实际行为、Trace Event、复现命令和修复建议。Canonical JSON 适合集成 CI，自包含 HTML 可归档并由浏览器打印为 PDF。

## 12. 它有什么商业化路径？

可以提供三层服务：一次性 Quick/Standard 风险体检，Deep Audit 加修复验证，以及接入客户 CI 的持续风险回归。当前项目证明了技术闭环，不宣称已有客户、收入或合规资质。

## 13. 下一步最重要的优化是什么？

先提高可信度：增加状态级副作用差分、私有用例和版本基线比较；再做 Run 级分布式调度与趋势统计；最后扩展动态红队、企业治理和浏览器/桌面 Agent。
