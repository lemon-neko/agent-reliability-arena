# 设计初衷：把 Agent 的可靠性变成工程证据

## 问题从哪里来

Agent Demo 通常展示一次顺利完成的任务，但真实产品更容易在重复运行、工具副作用、恶意输入和人工审批上暴露问题：第一次成功，第二次迷路；答案正确，却改坏了无关文件；看见检索文档中的 Prompt Injection，顺手泄露受保护信息；遇到高风险动作，本该暂停，却自行决定继续。

这些问题不能靠一张成功截图回答。团队真正需要知道的是：同一个 Agent 面对同一任务时是否稳定、过程是否守规、失败是否可解释、结果是否能复算。

## 项目要做什么

Agent Reliability Arena 把不同模型和 Runtime 放进相同版本的虚构副本，让它们在严格限定的工具和初始状态下反复运行。系统不仅保存最终回答，也记录模型回合、工具请求、工具结果、审批、错误、Token、成本和评分，形成可回放的 Trace。

它的目标不是替用户完成真实任务，而是观察 Agent 在受控任务中如何行动。

## 五个设计判断

1. **固定副本，而不是临时 Prompt。** 场景以 `id + version` 标识，并携带可复现 Fixture、工具白名单和确定性期望。
2. **最小权限，而不是相信模型自觉。** Agent 没有任意 Shell、通用 HTTP 或宿主文件访问；每个工具调用都经过 fail-closed Gateway。
3. **隔离运行，而不是共享测试环境。** 每个 Run 拥有独立临时目录、SQLite 副本和虚构文档，结束后清理。
4. **记录过程，而不是只保存答案。** Trace 让用户看到 Agent 如何成功、在哪里越权、何时等待审批，以及失败能否重现。
5. **确定性核心分，而不是让另一个 LLM 随心情改分。** 相同场景、状态和 Trace 必须得到相同核心评分；LLM Judge 最多提供旁路观察。

## 为谁服务

- 需要为 Agent 产品建立回归测试和发布门槛的工程团队。
- 比较模型、Runtime 或 Prompt 策略的 AI 开发者。
- 检查 RAG、工具调用、审批和安全边界的 QA 与安全人员。
- 希望用可验证工程证据展示 Agent 能力的开源作者和服务团队。

## 不是什么

- 不是让 Agent 直接操作真实生产系统的自动化平台。
- 不是只比较语言风格或主观偏好的聊天榜单。
- 不是已经具备统计显著性、海量任务和真实故障恢复的成熟 Benchmark。
- 不是安全沙箱产品；当前边界用于受控、虚构、可信主机上的评测。

## 长期愿景

项目最终希望形成一套可公开复验的 Agent Reliability CI：同一场景矩阵可在多个模型和 Runtime 上并行运行，评分能检查最终状态与副作用，失败可聚类，趋势可比较，公开报告中的每一项结论都能回到原始脱敏证据。

当前实现与愿景之间的距离见 [项目状态](status.md) 和 [路线图](roadmap.md)。
