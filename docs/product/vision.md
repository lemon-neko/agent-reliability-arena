# 设计初衷：给自研 Agent 做一次可复验的风险体检

## 为什么要做

Agent Demo 往往只展示一次顺利完成的任务，但上线风险藏在过程里：恶意内容会不会改变指令，密钥会不会进入回答，工具是否越权，高影响动作是否绕过人工审批，失败后会不会重复执行副作用，以及调用是否陷入循环。

一次成功截图回答不了这些问题。团队需要的是一套能自动重复、留下证据、给出修复方向并进入发布流程的工程化体检。

## 产品要做什么

Agent Reliability Arena 面向实现 `ara-step/1` 的 HTTP 工具型 Agent。用户注册自己的 Endpoint，选择 Quick、Standard 或 Deep 风险包，平台并发执行 12、72 或 180 次测试，在本机生成管理层摘要、技术 Finding、脱敏 Trace 和上线建议。私有 Prompt、Fixture 与完整 Trace 默认不离开本机；只有作者主动导出的脱敏证明包可以进入公开基准。

原有的多模型 Arena 仍被保留，用于对照 Runtime 和版本化场景；风险体检成为产品主流程。

## 六个设计判断

1. **检查过程，而不只检查答案。** 工具意图、审批顺序、错误、重试、资源消耗和最终回答共同构成证据。
2. **平台执行工具，而不信任 Agent 自报。** Agent 每一步只能返回一个意图，文件、SQL、检索、Secret、审批、模拟 HTTP 与模拟业务操作由平台校验并执行。
3. **固定测试包，而不是临时 Prompt。** 12 个基准用例与固定 Seed 变体让 12/72/180 次矩阵可以复现。
4. **确定性评分，而不是让另一个 LLM 决定门禁。** 相同测试包、版本、Seed 和 Trace 必须产生相同分数；Critical/High 风险会直接限制最终等级。
5. **默认私有，公开自愿。** 凭证值不持久化；公开证明包不含 Endpoint、Prompt、Fixture、凭证或完整 Trace。
6. **模拟副作用，而不碰真实业务。** 出站 HTTP 和高影响业务动作只命中本次 Run 的虚构 Fixture，不提供任意 Shell 或通用网络代理。

## 为谁服务

- 上线前需要风险门禁与回归测试的 Agent 团队。
- 自研 RAG、工具调用、审批流或业务 Agent 的工程与安全人员。
- 需要向客户或评审交付可检查风险报告的服务团队。
- 希望在统一测试条件下公开复验产品能力的 Agent 作者。

## 不是什么

- 不是法律、合规或绝对安全认证。
- 不是运行不可信代码的系统级沙箱。
- 不是让 Agent 直接操作生产账号的自动化平台。
- 不是依靠隐藏 LLM Judge 输出不可解释分数的聊天榜单。
- 当前不支持浏览器、桌面 Agent、任意 JSON 映射或 SaaS 计费。

## 长期愿景

把 Agent 风险体检变成持续集成中的发布门槛：版本变化自动触发固定与私有测试包，风险趋势可以对比，失败能聚类，报告能进入企业治理流程，公开榜单中的每项主张都能回到版本化测试条件与脱敏证据。
